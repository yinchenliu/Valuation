### `analysis/projector.py` — the ΔNWC sign, the assignment's centre of gravity

**The derivation, written before `projector.py:97` was opened.** Working capital growing
*consumes* cash, so the cash flow statement — which reports from the cash point of view
— shows the change as **negative**. Projected FCFF is `NOPAT + D&A − CapEx − ΔNWC`
(`models/valuation.py:80-81`, `:96-102`), i.e. it **subtracts** ΔNWC. Therefore, for a
growing working capital to **reduce** FCFF — which it must, because the cash left the
firm — `nwc_pct_revenue` has to be **positive**. So the derivation from the CFS figure
must carry a negation. The code agrees.

Three companies, identical but for working capital: revenue `1000`, margin `0.20`,
tax `0.25`, D&A `10%`, capex `5%`, one projected year at `0%` growth, so projected
revenue is `1000` in all three and

```
EBIT  = 1000 * 0.20      = 200
NOPAT =  200 * (1 - 0.25) = 150
D&A   = 1000 * 0.10      = 100
capex = 1000 * 0.05      =  50
FCFF  = 150 + 100 - 50 - dNWC = 200 - dNWC
```

| WC grew 50 (CFS `−50`) → `nwc_pct_revenue` | `+0.05`, and `> 0` | hand arithmetic `−(−50)/1000`, from the derivation above |
| WC released 50 (CFS `+50`) → `nwc_pct_revenue` | `−0.05`, and `< 0` | hand arithmetic `−(+50)/1000`. Releasing working capital is a *source* of cash, so the drag is negative |
| WC grew 50 → `fcff` | `150.0` | hand arithmetic `200 − (1000 × 0.05) = 200 − 50` |

### F1 — `analysis/normalizer.py:68` applies an *expense* sign convention to an *income*-signed field. New; on no backlog. `major`

`apply_adjustments` computes one delta and applies it to whichever field
`_resolve_field` returns:

```python
delta = -item.amount if item.direction == "add_back" else item.amount
```

That is correct for every **expense** line, where a larger value means smaller earnings.
`_LABEL_TO_FIELD` also maps three labels — `"other_non_operating"`,
`"other non-operating"`, `"non-operating"` (`normalizer.py:38-40`) — to
`other_non_operating`, and `NonRecurringItem`'s own docstring names that field as a
valid `line_item` (`models/financial_statements.py:16`). But `other_non_operating` is
**added** in `ebt` (`models/financial_statements.py:91`): a larger value means *larger*
earnings. The sign is therefore inverted for that field.

**Measured**, on revenue 1000 / COGS 400 / SG&A 200 / `other_non_operating` 80:

| | `other_non_operating` | EBT | net income |
|---|---|---|---|
| before | `80.0` | `480.0` | `480.0` |
| after `remove` of a one-time **gain** of 50 | **`130.0`** | **`530.0`** | **`530.0`** |
| a clean base | `30.0` | `430.0` | `430.0` |

The error is `+100` on a `50` item — **twice the amount, in the wrong direction** —
because the correct move and the applied move are equal and opposite. It is exactly the
`gain_loss_asset_sale` category the docstring lists, which is the single most common
non-operating NRI in a 10-K. It reaches net income, therefore the historical effective
tax rate, therefore `derive_assumptions`' `tax_rate`, therefore every projected NOPAT.

`interest_income` is the same shape and is not currently mapped; adding it to the table
would make the defect worse rather than better.

**What an assignment would need to decide:** put the sign on the field (a per-field
`is_expense` table), or move it onto `NonRecurringItem` (which already declares
`adjusted_impact` correctly for operating lines), or restrict `_LABEL_TO_FIELD` to
operating lines and stop on the rest. A test cannot be written until that is chosen.
**Recommend a backlog item and an assignment; I did not write this red.**
